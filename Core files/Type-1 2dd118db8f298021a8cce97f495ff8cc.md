# 📋 SHAPE UP PITCH

## Problem

Most requests are simple. The system treats them as complex. Users wait through unnecessary planning UI for obvious tasks.

*The broken pattern:*

```
User: "Put this dress on a model at the beach"
  ↓
System: "Let me plan this..."
  ↓
Shows: Space selection → Form → Stepper → Plan
  ↓
User waits 15-20 seconds for planning UI
  ↓
Finally: Image generates
  ↓
Result: Frustration. "Why didn't it just do it?"
```

*The data:* 80% of user requests don't need planning, explicit space selection, or multi-step workflows. They're direct execution requests.

*Real user pain:* "I asked ShopOS to remove the background. It showed me a plan, a form, a stepper. I just wanted the background removed. Why all the ceremony for a 2-second task?"

## Appetite

*2 weeks*

Type-1 routing is the difference between "AI assistant" and "AI workflow system." Users expect instant responses to simple requests. Without this, ShopOS feels slow and over-engineered.

We're investing 2 weeks because routing logic is straightforward: pattern matching + direct API calls. The complexity is getting it right 95% of the time.

## Solution

*Type-1 Routing = Instant Execution for Obvious Intents*

Not an orchestrator. A simple routing system that detects obvious requests and executes immediately.

*The Flow:*

```
User: "Put this coat on a model at the beach"
  ↓
Router checks:
  1. Image + instruction? ✓
  2. Obvious intent? ✓
  3. Type-1 pattern? ✓
  ↓
Route directly to image model (Nano Banana Pro)
  ↓
Streaming starts <2 seconds
  ↓
Output appears in Rich Gallery
  ↓
Model attribution visible (hover)
  ↓
No plan, no stepper, no form
  ↓
User: "Perfect. That's what I wanted."
```

*Type-1 vs Type-2:*

*Type-1 (Reflex):* Direct execution

- Examples: "Remove background," "Put dress on model," "Write caption," "Translate to French"
- Flow: Input → Route → Execute → Output
- UI: Rich Gallery only, no planning
- Speed: <2 seconds to streaming

*Type-2 (Reasoning):* Complex workflows

- Examples: "Launch product campaign," "Optimize my catalog for AI," "Create 20 ad variations"
- Flow: Input → Plan → Form → Execute → Output
- UI: Stepper, forms, progress tracking
- Speed: Variable (depends on workflow)

*Routing Decision Tree:*

```
Input received
  ↓
1. Exact Space match? (e.g., "Background Removal")
   → Yes: Open Space form (Type-1 if form auto-fillable)
   → No: Continue
  ↓
2. Image + simple instruction? (e.g., "Put on model")
   → Yes: Direct image API (Type-1)
   → No: Continue
  ↓
3. Text processing? (e.g., "Write caption")
   → Yes: Direct LLM API (Type-1)
   → No: Continue
  ↓
4. Specific API endpoint? (e.g., "Remove background")
   → Yes: Direct API (Type-1)
   → No: Continue
  ↓
5. Requires planning/retrieval/multi-step?
   → Yes: Show plan (Type-2)
```

*Key Principles:*

- *If intent is obvious, act immediately*
- *No planning UI for direct requests*
- *Always show what was assumed*
- *Model attribution mandatory*
- *Related Spaces suggested after output*

## Rabbit Holes

*Don't build:*

- *AI-powered intent classification.* Pattern matching is enough for 95% accuracy.
- *User confirmation for Type-1.* If we're not confident, route to Type-2.
- *Complex routing logic.* Keep decision tree simple, 5 checks max.
- *Per-user routing preferences.* Same input → same routing for all users.

*Reuse existing:*

- Rich Gallery (output rendering)
- Space forms (when needed)
- Model selection logic (default models)

*Watch out for:*

- False positives (Type-1 when should be Type-2)
- Ambiguous inputs ("Make it better" - what's "it"?)
- Assumption disclosure (user must know what we assumed)

## No-Gos

*Explicitly NOT doing:*

- ✖ AI-based routing (pattern matching only)
- ✖ User-configurable routing (same logic for all)
- ✖ Confirmation dialogs (defeats instant execution)
- ✖ Complex state management (stateless routing)
- ✖ Per-session learning (no memory of past routes)

# 🔧 ENGINEERING PRD

## 1. OBJECTIVE

*Purpose:*
Build a fast-path routing system that detects obvious user intents and executes them immediately without planning UI. Reduce time-to-first-output from 15-20 seconds to <2 seconds for 80% of requests.

*Goal:*

- *95% routing accuracy* (correct Type-1 vs Type-2 classification)
- *<2 seconds to streaming* (for Type-1 requests)
- *Zero planning UI* for Type-1 (no stepper, forms, plans)
- *100% assumption disclosure* (user knows what we assumed)
- *No Type-2 regression* (complex workflows still work)

*Context:*
Type-1 routing is the first interaction most users have with ShopOS. If simple requests feel instant, the product feels magical. If they require planning UI, it feels over-engineered.

## 2. SCOPE

### In Scope

*Routing System:*

- Pattern matching engine (detect Type-1 vs Type-2)
- 5-step decision tree (Space match → Image+instruction → Text → API → Plan)
- Direct API routing (image models, text models, specific endpoints)
- Stateless routing (same input → same route)

*Type-1 Patterns:*

- Image + simple instruction ("Put on model at beach")
- Text processing ("Write caption for this product")
- Specific API endpoints ("Remove background")
- Language translation ("Translate to French")

*Assumption Disclosure:*

- Show what was assumed (Space, model, parameters)
- Display in chat before/during generation
- Model attribution (hover state)

*Post-Generation:*

- Rich Gallery rendering
- Model attribution visible
- Related Spaces suggestions (2-3 lightweight cards)

*Integration Points:*

- Image models (Nano Banana Pro, others)
- Text models (Claude, GPT)
- Spaces (form auto-fill logic)
- Rich Gallery (output rendering)

### Out of Scope (Phase 2)

- AI-powered routing (neural classification)
- User preferences for routing
- Per-session learning
- Complex state management
- Confirmation dialogs

*Phase:* Phase 1 (Foundation) - 2 weeks

## 5. CORE REQUIREMENTS

### Routing Decision Tree

*Step 1: Exact Space Match?*

- Input: "Background Removal" or "Remove background from this image"
- Match: Space name in input text
- Action: Open Space form (if auto-fillable → Type-1, else → Type-2)

*Step 2: Image + Simple Instruction?*

- Input: Image attachment + instruction ("Put on model," "Change background," "Make brighter")
- Pattern: <image> + <verb> + <simple_descriptor>
- Action: Route to image model (Type-1)

*Step 3: Text Processing?*

- Input: "Write caption for this product" or "Generate description"
- Pattern: <verb> + <text_output_type>
- Action: Route to text model (Type-1)

*Step 4: Specific API Endpoint?*

- Input: "Remove background" or "Upscale image" or "Translate to French"
- Pattern: Known API command
- Action: Route to specific API (Type-1)

*Step 5: Requires Planning?*

- Input: "Launch product campaign" or "Optimize catalog for AI"
- Pattern: Multi-word complex task, no clear single action
- Action: Show planning UI (Type-2)

### Type-1 Pattern Recognition

*Image + Instruction Patterns:*

- "Put [item] on [context]"
- "Change background to [description]"
- "Make [item] [adjective]"
- "Show [item] in [setting]"
- "Place [item] on [surface]"

*Text Processing Patterns:*

- "Write [content_type] for [item]"

- "Describe [item]"

*API Endpoint Patterns:*

- "Remove background"

- "Crop to [dimensions]"
- "Translate to [language]"

## 6. BEHAVIORS & RULES

### Routing Confidence Thresholds

- *High confidence (≥95%):* Execute Type-1 immediately
- *Medium confidence (80-94%):* Execute Type-1 but flag assumptions prominently
- *Low confidence (<80%):* Route to Type-2 (planning UI)

### Stateless Routing

- Same input → same routing decision
- No memory of past requests
- No per-user customization
- No session-based branching

### Assumption Disclosure Rules

*Always disclose:*

- Selected Space (if any)
- Model used
- Image type (product, model, lifestyle)
- Number of outputs
- Style applied

*Never hide:*

- Which model generated output
- What parameters were assumed

### Fallback Behavior

*If Type-1 routing fails:*

1. Show error: "Couldn't generate automatically. Let's try planning."
2. Route to Type-2 (planning UI)
3. Log failure for routing improvement

*If ambiguous input:*

- Default to Type-2 (planning UI)
- Better to show planning than execute wrong thing

## 7. TECHNICAL CONSTRAINTS & EDGE CASES

### Performance Requirements

- Routing decision: <100ms
- Streaming start (Type-1): <2 seconds
- Model attribution render: <50ms
- Rich Gallery load: <200ms

### Pattern Matching Accuracy

- Target: 95% accuracy (correct Type-1 vs Type-2)
- Measure: Manual review of 1000 random requests weekly
- If accuracy <90% → Review patterns, add new rules

### Error Handling

*1. Pattern Match Ambiguous:*

- Example: "Make it better" (no context)
- Action: Route to Type-2, ask clarifying questions

*2. Model API Down:*

- Retry 2x
- If fails → Show error, offer Type-2 fallback

*3. Attachment Missing:*

- Example: "Put on model" but no image
- Action: Prompt user: "Please upload an image"

*4. Unsupported File Type:*

- Example: PDF attachment for image task
- Action: Show error: "Image required. Uploaded file type not supported."

### Edge Cases

*1. User Uploads 10 Images:*

- Type-1 pattern: "Remove background"
- Action: Batch process all 10 (Type-1 still applies)
- Show progress: "Processing 1 of 10..."

*2. Contradictory Instructions:*

- Example: "Put on model at beach" + "Use studio background"
- Action: Route to Type-2 (ambiguous, needs clarification)

*3. Very Long Instruction:*

- Example: 500-word detailed brief
- Action: Route to Type-2 (complex, needs planning)

*4. User Says "Plan This":*

- Override: Always route to Type-2 if user explicitly requests planning
